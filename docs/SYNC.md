# GitHub ↔ рабочая папка

Репозиторий: **https://github.com/AzFox1404/-**, ветка `main`.

## Правило последующих задач

В начале работы проверить удалённую main и `git status --short`. Учитывать изменения, которые пользователь внёс в эту папку вручную. Перед применением удалённых изменений сохранить пересекающиеся локальные правки отдельным коммитом/веткой; не делать reset --hard, clean или безусловное копирование поверх данных.

После исправления выполнить относящиеся к нему проверки, опубликовать коммит, проверить новую удалённую SHA и привести рабочую копию к тому же состоянию. Не требуется заново копировать неизменившиеся файлы или сканировать все клиентские документы.

## Два канала доступа

### Обычный Git, если авторизация на ПК настроена

```powershell
git status --short
git fetch origin
git log --oneline --left-right HEAD...origin/main
```

При отсутствии локальных правок можно применять fast-forward. При правках сначала сохранить и сопоставить их. В конце обычные commit/push и повторная проверка remote main. Учётные данные хранятся в штатном менеджере Git, не в проекте.

### Подключение GitHub в Codex

В текущей среде GitHub-коннектор авторизован, а HTTPS Git не имеет локального входа. Это не один и тот же доступ. Для первоначальной публикации и следующих задач без локального входа используется GitHub Git Data API через коннектор.

1. Прочитать head `main` через `fetch_commit`. При обновлении существующей копии сравнить последний опубликованный SHA (`.git/codex-sync/state.json`) с main через `compare_commits`.
2. Получить затронутые удалённые файлы коннектором. Применять только к отслеживаемым исходникам после сравнения с локальными правками. При конфликте сохранить обе версии и разрешить его, не теряя пользовательский код. Новые удалённые файлы не удалять молча.
3. Сформировать индекс Git и запустить `python tools/github_bundle.py export`. Это читает канонические staged blobs, не пользовательские документы. Пакет и состояние находятся внутри `.git/codex-sync/`, не публикуются.
4. Создать blob для бинарных ресурсов (`create_blob`, base64); для UTF-8 исходников передать content в `create_tree`. Дерево должно **совпасть** с SHA локального `git write-tree`.
5. Создать commit с родителем, равным проверенному head main. Обновить ref через `update_ref`, `expected_sha=<проверенный head>`, `force=false`. Если main изменилась, сначала перечитать и объединить изменения.
6. Сохранить фактические metadata созданного git-коммита в локальный JSON. `tools/github_bundle.py adopt <json>` принимает только коммит, чьи реконструированные байты дают ту же SHA и то же дерево. При неизвестной метаинформации не подделывать объект — получить её через коннектор.
7. Повторно проверить удалённый head, `git status`, `HEAD` и `origin/main`.

Первоначальная API-копия может иметь shallow-границу: исходный подписанный GitHub-коммит не загружался через неавторизованный Git. Полная история сохранена на GitHub; новые локальные и удалённые версии сопоставляются по SHA. После настройки обычного Git можно дополнить историю штатным fetch.

## Что никогда не синхронизируется автоматически

`Рабочая папка ИД/`, исходники компаний, заполненные акты, паспорта, OCR, резервные копии, временные результаты и `.project-local.json`. Код и документы разделены `.gitignore` и проверкой перед экспортом пакета.

Постоянный фоновый наблюдатель не установлен. Обновление выполняется в ходе задач агента, как требует `AGENTS.md`; без участия работающего агента или отдельно настроенной авторизации скрипт не может использовать доступ коннектора сам по себе.
